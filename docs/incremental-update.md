# 增量更新：可行性、收益与前置条件

> 结论先行：**可以做，而且收益很大**——文件级增量能把单次更新从 222 MB 压到约 20 MB（-90%）。
> 但"增量"只能在**文件粒度**上做，做不到字节级；并且必须先在发布侧和客户端侧补三样东西
> （文件清单、delta 包、本地安装状态）。
>
> 文中体积均为 2026-10-25 v1.11.0 产物实测值。

---

## 1. 现状为什么是全量

客户端拿的是 `zip-onedir` 整包，安装即整目录替换。清单里只有整包的 `size` / `sha256`，
没有任何"包内有哪些文件"的信息 —— 客户端无法知道自己本地差哪几个文件，自然也谈不上只取差异。

---

## 2. 体积构成（决定增量空间在哪）

| 部分 | 解包 | zip 内 | 跨版本变化 |
|---|---|---|---|
| 固定二进制依赖（cv2 / onnxruntime / pymupdf / numpy.libs / jieba / rapidocr / PIL） | **307 MB**（64%） | ≈ 110 MB | 基本不变 |
| 向量模型 `data/models/bge-small-zh-v1.5` | 90 MB | 52 MB | 不变（除换模型） |
| `Xwork.exe`（业务代码 + stdlib + PYZ 全在里面） | 18.3 MB | **18.7 MB** | **每次必变** |
| `_internal/web`（前端资源） | 1 MB / 14 文件 | ≈ 0.3 MB | 前端改动才变 |
| 其余 `_internal` 零散文件 | ≈ 65 MB | ≈ 25 MB | 偶发小改 |

合计解包 481 MB → zip 222 MB。

**两个关键实测事实**：

1. `Xwork.exe` 19175639 B → 压缩后 18709417 B（**97.6%，几乎不压缩**）。
   因为 PyInstaller 的 PYZ 本身已经压缩过，再套 zip 没有收益。
   → **exe 就是增量的下限**：只要业务代码改动，这 18 MB 必然要传。
2. 307 MB 的依赖库占总量 64%，而它们跨版本不动。
   → **增量的绝大部分收益来自"跳过这些不变的大文件"**。

所以：文件级增量的现实区间是 **18–25 MB**（exe + 前端 + 少量偶发文件），而不是几百 KB。

---

## 3. 三种做法

| | A. 文件级差分 | B. 代码外置 + 文件级差分 | C. 二进制 patch |
|---|---|---|---|
| 做法 | 只传新增/变更的文件 | 把 `core/` `api/` 以外部 `.py` 目录随包发，exe 只做引导 | bsdiff / `zstd --patch-from` 对 exe 做字节级差分 |
| 单次更新体积 | ≈ 20 MB | **< 1.5 MB** | ≈ 5–10 MB |
| 相对 222 MB | -90% | **-99%** | -95% |
| 实现成本 | 低（发布脚本 + 客户端比对） | 中（改打包方式 + 启动路径） | 高（每对版本都要做 patch） |
| 存储增长 | O(N) | O(N) | **O(N²)**：v1→v12 要 66 个 patch |
| 回滚 | 靠全量包 | 靠全量包 | 靠全量包 |
| 主要风险 | 残留文件、清单错位 | 源码明文可见、版本错配 | patch 应用失败后目录不可预测 |

**推荐 A，长期演进到 B，不推荐 C。**
C 的成本曲线是平方级的，而这个项目的版本节奏（一年几次）根本摊不平。
B 之所以值得，是因为**仓库已经是开源的**——"源码在安装目录可见"不再是缺点。

---

## 4. 方案 A 怎么落地

### 4.1 发布侧（每次发版多做三步）

```
① 打包 → 得到 dist/Xwork/（onedir）
② 生成 files-<version>.json：遍历目录，记 path / size / sha256
③ 与上一版本 files-<prev>.json 比对：
     新增或 hash 变化 → 打进 delta zip
     只在上版本存在   → 写进 remove.txt
   产出 delta-<prev>-to-<version>.zip
④ 全量包照旧产出（永不取消，它是回退链的底）
```

`files-<version>.json` 一份两用：**既算差异，也是"应用后应得到的目录状态"**。
没有它，增量装完无法证明目录是对的 —— 这是增量方案里最容易被省掉、也最致命的一环。

清单扩展示例（`schema` 升到 2）：

```json
{
  "platforms": {
    "win-x64": {
      "kind": "zip-onedir",
      "file": "xwork-1.12.0-win64.zip",
      "size": 232783872,
      "sha256": "…",
      "url": "https://github.com/gaio-x/xwork/releases/download/v1.12.0/xwork-1.12.0-win64.zip",
      "files": {
        "file": "xwork-1.12.0-files.json",
        "sha256": "…",
        "url": "https://github.com/gaio-x/xwork/releases/download/v1.12.0/xwork-1.12.0-files.json"
      },
      "deltas": [
        {
          "from": "1.11.0",
          "file": "delta-1.11.0-to-1.12.0.zip",
          "size": 21495808,
          "sha256": "…",
          "removes": 3,
          "url": "https://github.com/gaio-x/xwork/releases/download/v1.12.0/delta-1.11.0-to-1.12.0.zip",
          "mirrors": ["…"]
        }
      ]
    }
  }
}
```

### 4.2 客户端侧（四步，任一步不过就退回全量）

```
① 读本地 data/update/installed.json → 得到 {version, files[]}
② 在清单 deltas[] 里找 from == 本地 version 的条目；找不到 → 走全量
③ 下载 delta → 解压到 data/update/staging/ → 按 remove.txt 删除 → 
   用 files-<version>.json 逐文件校验 staging（size + sha256）
④ 全部通过 → 停进程 → 原子替换（旧目录改名 .old-<ver>）→ 起新进程
   任一文件不符 → 丢弃 staging（改名而非删除），走全量
```

`installed.json` 必须在**每次安装/更新成功后**重写，否则下一次算不出差异。
它同时是"用户手工动过 `_internal` 里文件"的检测手段 —— 本地 hash 与记录不符时，直接判为
"本地不干净"，走全量覆盖，避免把改坏的环境继续增量下去。

## 5. 需要的配置与条件

### 必须有（缺一项就做不成）

| # | 条件 | 现状 | 要做什么 |
|---|---|---|---|
| 1 | 每版产出 `files-<version>.json` | ❌ 无 | 改 `tools/build_exe.py`：打包后遍历产物算 hash |
| 2 | 客户端记录本地文件清单 | ❌ 无 | 新增 `data/update/installed.json`，安装后写入 |
| 3 | 保留上一版本完整产物 | ⚠️ 有 dist/ 历史目录，但无固定保留策略 | 每版留 2–3 个 onedir（约 1.5 GB 磁盘），供生成 delta |
| 4 | 清单 schema 支持 `deltas` / `files` | ❌ 现为 schema 1 | 升到 schema 2；**老客户端必须"不认识就拒更新"，不能猜** |
| 5 | delta 包 sha256 + 应用后全量校验 | — | 两级校验：包本身 + 落地目录逐文件 |
| 6 | 显式 `remove.txt` | — | 上版本有、本版本无的文件必须删；`_internal` 里残留旧 `.pyd` 会导致 import 错乱 |
| 7 | Release 附件存 delta | ✅ 上限 2 GB | 无需额外配置，单 delta 约 20 MB |

### 建议有（不做也能跑，但会埋坑）

| # | 条件 | 为什么 |
|---|---|---|
| 8 | 可复现构建（固定 PyInstaller 版本、`SOURCE_DATE_EPOCH`） | 同版本重建 hash 不同 → "重装后本地清单 ≠ 发布清单"，客户端会误判成"本地不干净" |
| 9 | delta 失败自动降级全量，全量失败自动换镜像 | 增量多了一条链路，失败点多一个，降级链必须更长而不是更短 |
| 10 | 回滚只走全量包 | delta 是单向的，反向 patch 要另存一套，成本翻倍不划算 |
| 11 | 增量日志单独记 | 出问题时能一眼看出"是差异算错还是替换错"，否则只有"更新失败"四个字 |

### 不需要的条件

- 不需要新账号、新服务、新存储：Release 附件够用。
- 不需要改镜像链：delta 与全量走同一套 `url` + `mirrors` + 代理降级。
- 不需要 GPU / 额外运行时：纯文件比对，标准库 `hashlib` 足够。

## 6. 什么时候**不该**做增量

- **跨过 `min_version`**：本来就要求"整包覆盖 + 提示先备份"，直接走全量。
- **依赖大版本换代**（PyInstaller、onnxruntime、Python 小版本升级）：文件级差异接近全量，
  delta 只多一层风险，没有收益。
- **一年只发两三次**：222 MB 经代理约 3.5 分钟（1.1 MB/s），为省 3 分钟引入一套差异机制，
  维护成本高于收益。**这条是本项目当前的真实处境，务必自己想清楚再决定做不做。**

## 7. 建议节奏

| 阶段 | 动作 | 工作量 | 收益 |
|---|---|---|---|
| P0（当前） | 全量链路跑通：清单 → 下载 → 安装 → 回滚 | 已在做 | 能用 |
| P1 | 发布侧产出 `files-<version>.json`，客户端落 `installed.json` | 小 | 本身不省流量，但**是所有后续优化的地基**，也能做"文件级诊断" |
| P2 | delta 包生成 + 客户端差异安装 | 中 | -90% 流量 |
| P3 | 业务代码外置，exe 退化为引导器 | 中大 | -99% 流量，且启动更快 |

**最小可行一步**：只做 P1。不引入 delta，但客户端从此知道"自己缺哪些文件"，
发布侧也能验证"两次构建之间到底变了什么" —— 这是判断"改动是否如预期"的最直接证据，
即使最终不做增量也不亏。

## 8. 与更新协议的关系

本文件是 [release-protocol.md](./release-protocol.md) 的补充：协议定义"必须有清单、必须校验、
必须降级"，本文件回答"包能不能更小"。两者互不替代 —— 增量做不做，协议里那几条校验纪律都不变。
